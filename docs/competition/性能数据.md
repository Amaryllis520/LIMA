## 采集方法

`scripts/measure_competition_run.py` 是独立的命令包装器，不判断漏洞，不改变
bundle、业务预算、运行时裁决、检测器或沙箱。宿主需安装 `requirements.txt`
中的 `psutil>=7.0.0,<8`（支持 Windows/Linux；本次 Windows 实测 7.0.0）。
无需 Docker、模型密钥或目标仓库即可演示：

```powershell
python scripts/measure_competition_run.py --output output/perf-demo.json --interval-seconds 0.2 -- python -c "import time; x=bytearray(10*1024*1024); time.sleep(2)"
```

**本地示例只是采集器演示，不是 OpenHarmony 实战性能，也不是检测效果验收。**
本次 Windows/Python 3.13 的实际 JSON 附在 #292 对应 PR 描述中。
可将任何显式授权命令放在 `--` 后；包装器以 argv 列表、`shell=False` 启动，
stdout/stderr 继承当前终端。JSON 不保存命令参数、完整环境或子进程日志；
诊断仅保留类别和相关 PID，不保存异常原文（其中可能包含凭证）。

| 字段 | 单位及含义 |
|---|---|
| `schema_version` | 当前为整数 `1` |
| `run_id` / `started_at_utc` | UUID / 带 UTC 偏移的 ISO 8601 开始时间 |
| `wall_time_seconds` | 单调时钟测得命令启动到结束的秒数；中断时包含清理耗时，发布文件耗时不计入 |
| `command_exit_code` | 被测命令原始退出码；未能启动为 `null`，中断后记录清理后的实际码 |
| `sampling_interval_seconds` | 请求的采样间隔（秒，默认 `0.2`，必须是有限正数） |
| `host.sampled_peak_rss_bytes` | 各次主进程及可见子进程 RSS 总和中的最大值（字节）；无有效样本为 `null` |
| `host.sample_count` | 至少读取到一个进程 RSS 的采样次数，部分成功的样本也计数 |
| `host.measurement_source` / `host.complete` | `psutil process tree RSS sum` / 是否未遇到已知漏采、权限问题或中断 |
| `container` | 未请求容器、Docker 不存在、目标不可访问或命令期间无有效容器样本时为 `null`，原因见 `diagnostics`；未请求时无需诊断 |
| `diagnostics` / `partial` | 去重的来源、原因、可选 PID / 命令运行被中断或启动失败等未正常完成标记 |

宿主不扫描全机进程，只遍历启动的主进程和已观察到的子进程；已观察到的子进程
即使脱离父进程仍继续尝试采集。任一进程失联或权限不足都会记录诊断并将
`host.complete` 置为 `false`，不会把不可读取的 RSS 冒充为 0；有部分读数时保留
已读进程之和。RSS 求和可能重复计算共享内存。进程读取并非同时发生，短命进程
和采样间隔内的波动可能漏掉；`complete=true` 仅说明未遇到已知采集失败，
**采样最大值不等于绝对峰值**。采集耗时、系统调度会使实际间隔大于请求值。
由子进程句柄确认的主进程正常结束不记作失联；子进程中途退出仍记录漏采诊断。

可选容器读数：在 `--` 前加 `--container <名或id>`。容器线程仅调用
`docker inspect --type container --format ...` 和 `docker stats --no-stream --format ...`，
每次 CLI 调用超时 2 秒，不阻塞宿主采样，不重启、重建或清理任何容器。
容器用 inspect 得到的 ID 固定采样目标；输出包含：

- `id`、`image`（配置镜像名）、`image_id`（镜像 ID）。
- `resource_limits`：`memory_bytes`、`memory_swap_bytes`、`nano_cpus`、
  `cpu_quota`、`cpu_period`、`cpuset_cpus`，保留 Docker 配置值；0/空值通常为
  未显式配置，`memory_swap_bytes=-1` 表示不限，不把这些值解释成实际使用量。
- `sampled_peak_memory_bytes`、`sampled_peak_cpu_percent`、`sample_count`、
  `measurement_source`、`complete`：本次有效样本的最大值和采集状态。
  内存来自 Docker CLI `MemUsage`，带显示精度的单位换算为字节，Linux 上可能扣除缓存，
  与宿主 RSS 口径不同。CPU 百分比来自 Docker 自身统计窗口的 CPU 时间差，
  多核可超过 100%；它是采样最大值，不是精确 CPU 峰值。
  方法说明也保存在 `memory_sampling` / `cpu_percent_sampling`。

Docker CLI 自身的统计窗口和请求耗时可能使容器间隔明显大于配置值；只接收命令
运行期间完成的样本。命令太短时可能没有容器样本，结果为 `null` 而非 0。
已有样本后采集失败则保留已有值，`container.complete=false` 并附诊断。
不读取或混用 cgroup `memory.peak` 生命周期数据。

命令失败仍保存 JSON，正常完成的测量器返回被测命令退出码。
配置或输出错误返回测量器错误码 `125`，stderr 打印 `collector_error` 和
`command_exit_code`（未启动时为 `None`）；若命令自身也返回 125，需结合 stderr
和 JSON 区分来源。Ctrl+C 停止本次启动的命令树、保存 `partial=true`，包装器
返回 130，JSON 保留命令清理后的实际退出码；不会重试命令或模型。
Windows 先挂起启动命令，加入无资源限额的独立 Job Object 后再恢复执行，
中断时终止 Job 内全部后代（包括父进程已退出且从未采样到的后代），
并以独立进程组及 `taskkill /T /F`、已观察进程清理作为补充；Linux
使用独立 session/process group，同时清理已观察到的后代。权限等原因导致
无法清理时会记录 `cleanup` 诊断。Linux 主动脱离进程组且从未被采样观察到的
进程无法保证被发现或清理。Windows 若环境不允许 Job 分配则停止本次命令、
记录 partial 并返回 125；Job 不设置业务资源限额，正常结束时关闭句柄不终止后代。

同名输出（包括符号链接）已存在时在启动命令前拒绝；写入同目录临时文件并
flush/fsync，再以硬链接原子发布，发布时若有竞争写入也拒绝覆盖。
输出文件系统需支持硬链接（Windows NTFS、常规 Linux 文件系统）；不支持时
返回 125，不退回可能覆盖数据的发布方式。输出错误时命令退出码仍打印至 stderr。

第一版不做阶段级计时、真实 token 成本、全机进程扫描或精确 CPU 峰值。
Windows 宿主测试及本地两秒演示已运行；Linux、真实 Docker 和 OpenHarmony
实际命令未在本次任务验证，容器字段由 Mock 测试覆盖。
